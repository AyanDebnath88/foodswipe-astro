## Phase 2 detail — Swipe & matching core (done)

Built directly against `swipe_sessions`/`room_participants`/`swipes`/`dish_swipes` via the Supabase client (RLS-guarded) — no new API routes for room/swipe logic, per the "lightweight" direction of this rewrite. The only HTTP call this phase makes is to the teammate's Phase 3 `/api/suggest-cuisines` (match fallback).

- **Rooms (Task 1)** — `src/lib/rooms.ts`: `createRoom()` generates the id client-side (`crypto.randomUUID()`) and inserts `swipe_sessions` then `room_participants` in two statements, deliberately avoiding a `.select()` read-back (the "select if participant" RLS policy can't pass until the second insert has run — see the function's header comment). `joinRoomByCode()` calls the new `join_room_by_code()` RPC (`0005_room_join_rpc.sql`) rather than a direct `.select()`, because a joiner isn't a participant yet and can't pass that same RLS check to look the room up by code in the first place — classic chicken-and-egg, same shape as the `get_room_profiles()` problem `0001_init.sql` already solved, so this reuses that SECURITY DEFINER RPC pattern. The RPC also auto-flips `status` from `waiting` to `swiping` once a 2nd participant joins (mirrors the reference app's `db.joinRoom()`).
- **Guest join (Task 1)** — `src/lib/guest-auth.ts`'s `ensureGuestSession()`: reuses any existing session as-is, otherwise `signInAnonymously()`, then UPDATEs (never INSERTs) `profiles.display_name` — the row already exists from `handle_new_user()`. Deep link: creating a room now surfaces both the raw code and a `/rooms/join?code=XXXX` link (`src/components/rooms/join-by-link.tsx`), which prompts for a display name only when no session exists at all, then auto-joins.
- **Dietary filter (Task 2)** — `supabase/migrations/0004_room_dietary_filter.sql` seeds honest, per-cuisine `dietary_tags` (see that file's header comment for the reasoning behind each cuisine's tag set — deliberately not uniform). Filter itself is a **client-side filter**, not a Postgres function (`src/lib/dietary.ts`): both inputs (the ~9-row cuisine catalog and the room's participant list via `get_room_profiles()`) are already in the swipe UI's state before any deck renders, so a server round trip would add latency for no security benefit (deck contents are a UX nicety, not an access-control boundary — RLS/the match trigger don't depend on it). Recomputed via `useMemo`/effect whenever participants change.
- **Realtime sync (Task 3)** — `0008_enable_realtime.sql` adds `swipe_sessions`/`room_participants`/`swipes`/`dish_swipes` to the `supabase_realtime` publication (idempotent via a `pg_publication_tables` guard — **note: this only works against a project where Realtime is already enabled at the project level**, which the dashboard does by default, but if a from-scratch project ever has it off, publication membership alone won't turn it on). `src/lib/rooms.ts`'s `subscribeToRoom()` is the one shared channel factory (`room:${roomId}`, filtered `postgres_changes` per table) — every room/swipe/dish-swipe React island uses it instead of the reference app's 2-second polls.
- **Match detection (Task 4)** — server-side only, via `AFTER INSERT OR UPDATE` triggers: `check_swipe_match()` (`0006_match_detection.sql`) for cuisine matches, `check_dish_swipe_match()` (`0007_dish_swipes.sql`) for dish matches. Both SECURITY DEFINER (required — they run regardless of who's swiping, and "only creator can update status" RLS would otherwise block a non-creator's swipe from completing a match), both count current-`room_participants`-only right-swipes vs. participant count, both guarded against re-firing once already matched. Clients never compute or claim a match — they only react to `swipe_sessions` changing via Realtime. Traced by hand for a 3-participant room in both migration files' header comments.
- **Match fallback (Task 5)** — `src/lib/ai-suggestions.ts` calls `POST /api/suggest-cuisines` exactly to the agreed contract, swallowing any failure (network error, 404 if the route isn't deployed yet, etc.) into an empty array — never blocks the swipe UI. Auto-triggers once the deck empties with no match; **capped at 2 automatic refill rounds per room** (a documented, arbitrary-but-reasonable threshold — see `swipe-area.tsx`'s `MAX_AUTO_FALLBACK_ATTEMPTS`) so a room that rejects everything (including the AI's picks) doesn't hammer the endpoint forever. The manual "Stuck? Get AI suggestions" button has no cap. AI-suggested names that match an existing catalog cuisine are resolved to the real row (and still dietary-filtered); names that don't match anything become an unfiltered synthetic card (`syntheticCuisineFromName()` in `src/lib/cuisines.ts`) since there's no dietary metadata for a name the AI invented.
- **Swipe deck UI (Task 6)** — `src/components/swipe/{swipe-area,cuisine-card}.tsx`, `src/pages/swipe.astro` (now always room-scoped; solo swiping without a room is out of scope for this phase, deferred to Phase 4 per the roadmap). Cuisine artwork is a gradient tile + emoji, not photography — `0002_seed_cuisines.sql` already deferred real images to Storage in a later phase, so no new image-hosting dependency was added here either.
- **Dish-level room sync (Task 7 — the P0 fix)** — new `dish_swipes` table (`0007_dish_swipes.sql`), same RLS/upsert/trigger shape as `swipes` one level down (scoped to `restaurant_name` + `dish_name`, since a room can browse more than one candidate restaurant). `swipe_sessions` gained `matched_restaurant_name`/`matched_dish_name` columns and a `dish_matched` status value. `restaurant_name` is plain `text`, not a foreign key — there's no restaurants table in this rebuild yet (restaurant data is ephemeral/API-sourced from Phase 3), so a text scope key is the deliberately simple stand-in the task asked for. UI: `src/components/dishes/{dish-swipe-area,dish-card}.tsx`, `src/pages/match/[cuisine]/[restaurant].astro` — same Realtime-driven, server-decides-the-match pattern as the cuisine deck.
- **Match reveal page (Task 8)** — `src/components/match/match-reveal.tsx`, `src/pages/match/[cuisine].astro`. Reveal moment (heading, meal-time-of-day copy, "You all want X!") plus, since the integration pass, real restaurant discovery: geolocation requested on an explicit tap (not on mount — an unprompted permission dialog is the fastest route to a permanent denial), `POST /api/find-restaurants`, sponsored placements merged in via `mergeSponsoredFirst()`. Manual restaurant-name entry kept as a fallback for when geolocation is unavailable/denied or nothing nearby fits. See "Integration pass" below.

**Bug caught during verification**: `src/pages/swipe.astro` and (originally) `src/pages/rooms/join.astro` read query-string params (`?room=`, `?code=`) to decide page behavior. Astro's default output is static/prerendered at *build* time, when there's no query string at all — a naive implementation would have baked in a permanent wrong result (e.g. `/swipe` always redirecting to `/rooms` regardless of what `?room=CODE` a real request carried). Fixed two ways: `swipe.astro` now has `export const prerender = false` (reads `Astro.url.searchParams` per-request, same pattern as `login.astro`); `rooms/join.astro` instead reads `?code=` client-side inside the `JoinByLink` island via `window.location.search`, which let it stay static (cheaper, and it needed the browser for session/localStorage access anyway). Worth checking for this same trap in any future page that both wants static output and reads the query string.

## Phase 3 detail — Restaurant discovery & AI (done)

Four API routes under `src/pages/api/` (all `export const prerender = false`, all plain `fetch` — no Genkit, no SDK wrapper, per the AI-calls pattern below):

- **`POST /api/suggest-cuisines`** — the HTTP contract Phase 2's match-fallback logic depends on. **Implemented exactly as specified, verified byte-for-byte against the spec:**
  ```
  body:     { likedCuisines: string[], dislikedCuisines: string[], numberOfSuggestions?: number }
  response: { suggestedCuisines: string[] }
  ```
  Direct Gemini REST call (`gemini-2.5-flash`, `generateContent`, `responseMimeType: application/json` + `responseSchema` for structured output, `thinkingConfig.thinkingBudget: 0` — cuts token cost ~19x for this simple task, verified 950 tokens with thinking vs. ~50 without, same prompt). On any Gemini failure, falls back to picking cuisines from the `cuisines` table the caller hasn't already liked/disliked (via `createSupabaseServerClient`), and if that also fails (e.g. no live Supabase project — see Manual steps), falls further to a hardcoded 9-cuisine list. Never returns an error response for a well-formed request — matches Task spec's "never hard-fails the caller."
  Live-tested: `{"likedCuisines":["Italian","Japanese"],"dislikedCuisines":["Mexican"],"numberOfSuggestions":3}` → `{"suggestedCuisines":["French","Thai","Mediterranean"]}`.

- **`POST /api/find-restaurants`** — `{ cuisine, latitude, longitude }` → `{ restaurants: Restaurant[], source: "geoapify" | "mock" }`. Direct Geoapify Places API call (`catering.restaurant` category, same semantic name/tag matching + reordering as the reference file). No Yelp path ported (reference's `YELP_API_KEY` was never configured and the task only asked for Geoapify). Regional mock fallback (India/UK/generic) preserved for when Geoapify is unreachable or empty. Live-tested at Kolkata (22.49, 88.39) for "Indian" cuisine — returned 6 real restaurants from OpenStreetMap-backed data (e.g. "Rashika South Indian Snacks", "Machhranga Airconditioned Multi Cuisine", "Banzara A. C. Restaurant" with its real website `banzara.co.in`), `source: "geoapify"`.

- **`POST /api/restaurant-menu`** — `{ restaurantName, cuisine, restaurantWebsite? }` → `{ menu: Dish[], source: "gemini" | "fallback" }`, `Dish = { name, description, isTopPick }`. Direct Gemini REST call asking for a 7-10 dish menu with 2-3 top picks (structured-output schema, same prompt shape as the reference Genkit flow). Fallback (key missing or call fails) pulls `dishes` from the `cuisines` table by id/name match, else a generic 5-dish list — same first/third-item top-pick marking as the reference. Live-tested for "Banzara A. C. Restaurant" / Indian — got a real 8-dish Gemini-generated menu (Paneer Tikka Masala, Chicken Biryani, Butter Chicken marked as top picks), `source: "gemini"`.

- **`POST /api/delivery-links`** — `{ restaurantName, latitude, longitude }` → `{ services: { serviceName, url }[], region }`. Same regional service selection and search-URL structure as the reference `find-delivery-prices.ts` (India → Zomato/Swiggy, UK → Deliveroo/Just Eat/Uber Eats, EU → Wolt/Lieferando/Uber Eats, else DoorDash/Uber Eats/Grubhub) but **deliberately not a straight port**: the reference file's per-service prices were fabricated (hardcoded formulas, no real pricing API), which is explicitly out of scope per the revenue plan — real delivery pricing/affiliate integration is Phase 5. This endpoint returns search deep-links only, no price shown anywhere. ~~No affiliate tracking IDs in the URLs yet~~ — **superseded by Phase 5**: the response is now `{ services: { serviceName, url, affiliate }[], region, affiliateDisclosure }` (purely additive, nothing removed), and links are decorated when a program is configured. None is configured today, so the emitted URLs remain byte-identical to what this phase shipped. Live-tested both India (22.49, 88.39 → Zomato/Swiggy) and UK (51.5074, -0.1278 → Deliveroo/Just Eat/Uber Eats) coordinates.

Shared helper: `src/lib/ai/gemini.ts` — `generateGeminiJson<T>()`, one place all Gemini calls in this project should go through (endpoint, model, schema/thinking-budget wiring). Reuse this for any future Gemini call rather than re-implementing the fetch.

`GEMINI_API_KEY` / `GEOAPIFY_API_KEY` are real working keys now in `.env` (server-only, no `PUBLIC_` prefix, confirmed `git check-ignore` clean) — copied from the reference project's `.env.local`. `src/env.d.ts`'s `ImportMetaEnv` interface was extended with these two (typed `string | undefined` since they're allowed to be absent — the whole point of the fallback paths).

Not tested live: the Supabase-backed fallback branches in `suggest-cuisines` and `restaurant-menu` (they only trigger when Gemini itself fails, which wasn't forced during verification, and there's no live Supabase project yet anyway per Manual steps — a fetch against the placeholder URL there would fail safely into the next fallback tier, by inspection, but this is not the same as an observed live test).

## Phase 4 detail — Retention loop (code done, `0014` pending)

Why the phase existed: the app had no reason to be reopened between group sessions — nothing captured whether the group actually went, there was no history, no favourites, and no solo value at all outside a live room. Three things were built.

**1. Post-meal feedback** — new `session_feedback` table (`0014`), one row per `(session, member)`, unique on that pair so answering twice **edits** rather than duplicates (`src/lib/feedback.ts` upserts on `onConflict: "session_id,user_id"` — which is also why the constraint is a plain two-column UNIQUE and not a `lower()` expression index: PostgREST's upsert takes conflict *columns*). `did_go` is the only required answer, because "the plan died" is real data and must be one tap; `rating` is 1–5, nullable, and constrained to require `did_go` (rating a meal nobody ate is noise in the flywheel the table exists to feed). SELECT is room-wide via the existing `is_room_participant()` helper — deliberately, since "we went, it was a 5" is worth more to the group than to one person — while INSERT/UPDATE require **both** `user_id = auth.uid()` **and** participation (either half alone is a hole: room-uuid-only writes, or filing feedback in a co-participant's name). DELETE-own is allowed so feedback is retractable. A guard trigger freezes `id`/`session_id`/`user_id`/`created_at` and server-sets `updated_at` — RLS is row-level, so "which columns" always needs a trigger (same lesson as 0013 block B); without it a member could re-home their row into a room they've left. Realtime enabled (publication **and** `replica identity full`). UI: `src/components/feedback/feedback-prompt.tsx` — a card, never a modal, never gating anything; "Not now" is remembered per session in `localStorage` but leaves a one-line way back in, and every state has an exit (Cancel / Edit / Remove).

**2. Solo value: history + favourites** — `/history` (`src/components/solo/history-view.tsx`) and `/favorites` (`favorites-view.tsx`).
- **History added NO table.** Every part of it already existed: `room_participants` (which rooms, `joined_at`), `swipe_sessions` (status, matched cuisine, created_at), `dish_matches` (restaurant + agreed dishes + order), `session_feedback` (how it went). A `session_history` table would be a trigger-maintained denormalised copy that goes wrong the first time a trigger is missed; the query can't drift from itself and is already RLS-correct for exactly the right audience. `src/lib/history.ts`'s `fetchMyHistory()` does it in five batched queries, never N+1.
- **`saved_restaurants`** is the only table in this schema that is **not** room-scoped, so it's the one table whose policies do not go through `is_room_participant()` — ownership is the entire policy. `source_session_id` is `ON DELETE SET NULL`, not CASCADE: a creator closing a room must never silently delete other people's saved restaurants. `website` is CHECK-constrained to `^https?://` because that value is rendered as an `<a href>` and originates from a third-party places API — a `javascript:` URL there is a stored-XSS shape, so the column is the boundary (`safeWebUrl()` in `src/lib/favorites.ts` mirrors it client-side).

**3. Async rooms** — also **no new schema**. "Who has and hasn't swiped" is `exists a swipes row for (room, user)`, "how far along" is a count, "last active" is `max(created_at)` over that member's swipes; all read through policies that already exist, so a late arriver sees the current state with no new grant. `src/lib/history.ts`'s `fetchRoomProgress()` derives it; `src/components/solo/room-progress-panel.tsx` renders it, live over the existing `subscribeToRoom()` channel, and names who the room is waiting on (the in-app substitute for the notifications this phase was explicitly not to build). **A `last_seen_at` column on `room_participants` was considered and rejected** — it needs a client UPDATE policy on the table that is the key to every other policy in the schema (0013 block C spent a section removing exactly that), which then needs another guard trigger, all for a timestamp that `max(swipes.created_at)` already approximates *more honestly* (when someone last did something, not when a tab was left open).

**Deliberate UI restraint worth keeping**: the async panel shows per-member **counts only, never swipe directions**, even though `"swipes: select if participant of session"` would happily return them. "Ben liked Italian" rendered before the group has matched turns an independent vote into a bandwagon and quietly breaks the unanimity model. The read is allowed; the render is not. This is written into 0014's block D as well so nobody "improves" it later.

**Known limitation, stated rather than hidden**: history hangs off the `room_participants` row, and `leaveRoom()` hard-DELETEs it — it has to, because both match triggers count participant rows as the unanimity denominator and a ghost member deadlocks a room forever. So **leaving a room also erases it from your history**. The right fix is a soft leave (`left_at timestamptz`, with both match triggers and every membership policy counting only `left_at is null` rows); that changes the match triggers, so it is the next schema change this feature wants, not a Phase 4 change. The `/history` page says so in plain English rather than looking broken.

**Where the feedback prompt is NOT yet mounted**: the brief asked for it "after the order summary", which lives in `src/components/dishes/dish-swipe-area.tsx` — a file Phase 4 did not own (two other agents were working in this repo concurrently). It is mounted on every qualifying room card on `/history` instead, and the component is drop-in ready: `<FeedbackPrompt sessionId={room.id} userId={userId} roomCode={room.code} restaurantName={restaurantName} />` inside the "Done — show our order" summary is the whole change.

## Phase 5 detail — Monetization hooks (code done, `0015` pending)

Scope was channels 1 and 2 of the revenue plan only — delivery affiliate commissions (lowest lift, the link surface already existed) and *groundwork* for sponsored placement. Subscriptions, payments, Stripe and ads were explicitly excluded and none of them were built.

### THE SPONSORSHIP GUARDRAIL — read this before touching anything sponsorship-shaped

**Sponsored placement may only ever affect which *restaurants* surface AFTER a cuisine has already been matched. It must NEVER influence the cuisine swipe deck or the match algorithm.** This is not a preference to be traded off later against revenue: the app's promise to a group is "swipe to decide fairly", and the moment money can tilt what the group appears to agree on, that sentence is false and the product is quietly manipulating a social decision between friends. A group that has already chosen Thai may be shown a clearly-labelled paid Thai restaurant. A group must never be nudged into wanting Thai because someone paid.

It is enforced **structurally**, not by anyone remembering it:
- `sponsored_placements` is reachable from nothing on the matching path. Neither match trigger is touched by `0015`, the `cuisines` catalog doesn't reference it, `swipes`/`dish_swipes` don't reference it.
- `sponsored_placements.cuisine_id` is deliberately **not** an FK into `public.cuisines`. Partly the same reason `swipes.cuisine_id` isn't one (synthetic `ai-<slug>` cuisines), but mainly because an FK is a coupling — it would put a sponsorship row into the dependency graph of the catalog the deck is built from. There must be no edge in that direction at all.
- `fetchSponsoredPlacements()` **requires an already-matched cuisine id** as input, and returns restaurants. There is no code path in `src/lib/sponsored.ts` that returns, ranks or orders a cuisine, so it cannot seed a deck even by accident.
- `scripts/test-monetization.mjs` section 04 asserts permanently that no matching-path file (`src/components/swipe/**`, `src/lib/{cuisines,ai-suggestions,dietary,swipes}.ts`, `/api/suggest-cuisines`, migrations 0006/0007/0009/0012) so much as contains the string "sponsor", and that 0015 defines no trigger on a matching table. **If someone wires sponsorship into matching, that section goes red.** Don't "fix" it with an exception.

### 1. Affiliate-ready delivery links (live now — no migration needed)

- **`src/lib/affiliates.ts`** — the one config layer, server-only (never import it from a React island; it reads un-prefixed env vars). Maps all nine services to an env-var driven affiliate format: `AFFILIATE_<SERVICE>_TEMPLATE` (a network redirect template containing `{url}`, optionally `{id}` — how Impact/Awin/CJ/Cuelinks all actually work), `AFFILIATE_<SERVICE>_ID`, and the rarer `AFFILIATE_<SERVICE>_PARAM` for direct-parameter attribution. **Link formats are deliberately not hardcoded**: they are account-specific (publisher id, campaign id, merchant id) and networks change them, so a guessed format produces links that look configured and attribute nothing. The operator pastes their real template from their dashboard. `.env.example` documents each program, its usual network and where to sign up.
- **Zero configuration is the tested default**, because it is today's real state — no program has been signed up for. With nothing set, every link is emitted byte-identically to before. Every failure path (template with no `{url}`, non-https template, `{id}` with no id, unparseable result, an id with no format at all) falls back to the **plain working link** and logs once. A monetization misconfiguration must never cost the user their delivery link.
- **`/api/delivery-links` response is now** `{ services: { serviceName, url, affiliate }[], region, affiliateDisclosure }` — additive, nothing removed. `affiliate` is per-link because a region is routinely a mix of signed-up and not-signed-up services.
- **Disclosure is truthful in both directions.** `affiliateDisclosure` is true only when a link really was tagged, so with no programs configured the app shows no disclosure (claiming a commission we don't earn is its own small lie) and the moment one is configured the line appears with no code change. `rel="sponsored"` is likewise applied per-link, not to the whole list.
- **Click tracking** — `src/components/delivery/track-click.ts` writes `monetization_events` through the ordinary RLS-guarded browser client. No API route, no third-party SDK, no pixel. It returns `void`, not a promise, so a caller **physically cannot await it** and serialise a navigation behind an analytics write; the anchor is a real `href`/`target` and works with the tracking write failing entirely. Privacy: no IP, no user agent, no device id, no coordinates — only the app's own `auth.uid()` (which the client can neither omit nor forge: column default plus RLS), and rows cascade away with the user.
- **`src/components/delivery/delivery-options.tsx`** is the island. **Mounted** in the dish order summary (`dish-swipe-area.tsx`) since the integration pass — see "Integration pass" below.

### 2. Sponsored placement — schema + API only, NOT wired into the match UI

- `sponsored_placements` (see Schema below) + **`src/lib/sponsored.ts`** + **`POST /api/sponsored-restaurants`** (`{ cuisine, latitude?, longitude?, countryCode?, limit? }` → `{ sponsored: SponsoredRestaurant[] }`). `cuisine` is **required** — that requirement is the structural expression of the guardrail, since there is no way to call it without naming a decision the group already made.
- Sponsored entries are **structurally distinguishable**: every one carries `isSponsored: true` (a literal type, so TypeScript itself stops one being assigned into an organic restaurant type) and `sponsorshipLabel: "Featured"`. Paid results must never be silently blended into organic ones — a paid result the user can't identify as paid is the actual harm.
- Targeting **fails closed**: a placement targeting a country we can't confirm, or a radius around a point we don't have, is *not served* rather than served everywhere.
- Two queries (`.eq()` + `.is()`) instead of one `.or()`, deliberately: PostgREST's `.or()` takes a filter *expression*, so interpolating a user-supplied cuisine into it is exactly the injection this project already found and fixed in `/api/restaurant-menu`. Asserted in the suite.

### 3. Revenue instrumentation

Funnel = **matches reached → delivery links shown → link clicked**. "Matches reached" is **derived from `swipe_sessions`, not stored as an event** — duplicating it would let the two disagree and would let a client inflate the top of the funnel. Two service-role-only views (`monetization_funnel`, `monetization_clicks_by_service`) do the aggregation; they are `revoke`d from `anon`/`authenticated` because a Postgres view runs with its **owner's** privileges by default, so granting one to users hands them everyone's aggregate behaviour.

**Stated honestly rather than hidden**: `monetization_events` rows are client-reported, so a determined user could insert plausible events for themselves. That is fine for our own funnel diagnostics and is **not billing-grade** — if sponsored placement ever bills per click, that click must be counted where a client cannot write (a signed server endpoint, or the affiliate network's dashboard, which is the system of record for commissions anyway). Written into the migration too.

### No fabricated data — the rule that shaped this whole phase

The reference app's `find-delivery-prices.ts` returned **hardcoded fabricated prices presented as real**; Phase 3 deleted it. Phase 5 was the obvious door for that to come back through and it did not: no prices, no ratings, no invented commissions, no "X people ordered this" social proof anywhere. The suite asserts no `price`/`rating`/`eta`/`commission` field appears in any delivery response. Where a number isn't real, there is no number.

## Product decisions baked into this rebuild (don't relitigate these)

Four P0 gaps were found in the original app and are being fixed *during* the rebuild, not as backlog:
1. **Guest join** — joining a room via shared code/link must not require a real account. Implemented via Supabase Anonymous Auth (`signInAnonymously()`), which issues a real `auth.users` row/UUID so RLS works uniformly for guests and registered users alike. No parallel guest-id scheme.
2. **Dietary/allergy filter** — a room must never surface a cuisine that conflicts with any participant's stated restrictions.
3. **Match fallback** — unanimous-right-swipe matching can stall for 3-4 person rooms. After the deck is exhausted with no match, auto-trigger AI cuisine suggestions rather than leaving the room stuck.
4. **Dish-level room sync** — the old app synced the cuisine swipe across the room but let each person pick the final dish alone. The rebuild extends group sync all the way to dish choice.

5. **Multiple dishes per meal (the multi-dish model)** — a dish reaching unanimity must NOT end the session. Groups sitting down together order several dishes: a starter, a couple of mains, a dessert. The original design set `swipe_sessions.status = 'dish_matched'` plus scalar `matched_restaurant_name`/`matched_dish_name` on the first agreed dish and the UI rendered a terminal "The group decided!" screen — found in real two-user testing, and wrong twice over: it ended the session with most of the order still undecided, and nothing in the schema or UI could move a room back out of `dish_matched`. As of `0012_dish_matches.sql` an agreed dish is an **appended fact** in `dish_matches`, the room's status is untouched, and the group keeps swiping the rest of the menu with a live-updating agreed list. The only thing that ends a dish session is the user pressing "Done — show our order", which is reversible. Don't reintroduce a terminal dish state.

6. **Sponsored placement must never influence matching.** A revenue channel may only affect which *restaurants* surface after a cuisine is already matched — never the cuisine swipe deck, never the match algorithm. If sponsorship could tilt what a group "agrees" on, the core promise ("swipe to decide fairly") stops being true. As of Phase 5 this is no longer just a note to keep in mind: it is enforced structurally (no reachable path from the matching tables/components to `sponsored_placements`, no FK into the cuisine catalog, a read helper that requires an already-matched cuisine and can only return restaurants) and asserted permanently by section 04 of `scripts/test-monetization.mjs`. Full reasoning under "Phase 5 detail" above. **Don't relitigate this one at all** — if a future change seems to need sponsored data near matching, it doesn't.

## Schema (supabase/migrations/)

- `0001_init.sql` — `profiles`, `swipe_sessions`, `room_participants`, `swipes`. Full RLS. Includes a `is_room_participant(room_id)` SECURITY DEFINER helper (avoids self-referencing RLS recursion on `room_participants` — reuse this pattern for any new room-scoped table/policy, don't reinvent it) and a `get_room_profiles(room_id)` SECURITY DEFINER RPC that exposes only `display_name`/`dietary_restrictions`/`is_guest` to co-participants — `phone` and other columns stay owner-only. This RPC is the correct way to read another participant's info; don't add a row-level co-participant SELECT policy directly on `profiles`, it would leak `phone`.
- `0002_seed_cuisines.sql` — `cuisines` table (`id`, `name`, `dishes text[]`, `dietary_tags text[]`) seeded with the 9 real cuisines ported from the old project. **`dietary_tags` was left empty in this migration** — Phase 2 needs to seed real values (see below) or the dietary filter is a no-op.
- `0003_profile_trigger.sql` — `handle_new_user()` trigger populates `profiles` from `auth.users.raw_user_meta_data` on signup, sets `is_guest` from the real `is_anonymous` column (not "email is null" — that misclassifies OAuth/phone-only accounts).
- `0004_room_dietary_filter.sql` — seeds real `dietary_tags` onto the 9 `cuisines` rows (per-cuisine honest judgment calls, documented inline).
- `0005_room_join_rpc.sql` — `join_room_by_code(p_code)` SECURITY DEFINER RPC: the only way a not-yet-a-participant can join a room by its 4-letter code (a direct `.select()` can't work — see Phase 2 detail above). Also auto-flips `waiting` → `swiping` at 2 participants.
- `0006_match_detection.sql` — `check_swipe_match()` trigger on `swipes` (`AFTER INSERT OR UPDATE`): sets `swipe_sessions.status = 'matched'` / `matched_cuisine_id` the moment every current `room_participants` row has a `right` swipe on the same `cuisine_id`. SECURITY DEFINER, guarded against re-firing once matched.
- `0007_dish_swipes.sql` — new `dish_swipes` table (`session_id, user_id, restaurant_name text, dish_name text, direction, created_at`; `restaurant_name` is plain text, not a FK — no restaurants table exists yet), same RLS shape as `swipes`. Adds `matched_restaurant_name`/`matched_dish_name` columns and a `dish_matched` status value to `swipe_sessions` (widens the status check constraint). `check_dish_swipe_match()` trigger mirrors `check_swipe_match()` one level down, scoped to `(restaurant_name, dish_name)`.
- `0008_enable_realtime.sql` — adds `swipe_sessions`/`room_participants`/`swipes`/`dish_swipes` to the `supabase_realtime` publication (idempotent, guarded via `pg_publication_tables`). Needed for Realtime `postgres_changes` subscriptions to fire at all — RLS alone doesn't enable it.
- `0009_fix_join_match_realtime.sql` — four bugs the live e2e suite found the first time 0001-0008 ever ran against real Postgres. (1) `join_room_by_code()` always failed with an ambiguous `status` reference, so **nobody could ever join a room**; (2) both match triggers gated on `participant_count > 0`, so a host swiping alone matched instantly — now `>= 2`; (3) room creation's two client inserts could strand an unrecoverable room, replaced by an atomic `create_room()` SECURITY DEFINER RPC plus a creator-DELETE policy; (4) Realtime delivered zero events until `replica identity full` was set on every published table. Also adds the `room_participants` **DELETE policy** ("leave own row") that makes a real leave possible.
- `0010_fix_create_room_codegen.sql` — `create_room()` used `gen_random_bytes()` (pgcrypto, installed in the `extensions` schema) while declared `set search_path = public`, so every call failed. Room codes are now four random A-Z letters from built-in SQL; they're a human-typeable handle, not a security boundary.
- `0011_creator_can_see_own_rooms.sql` — `swipe_sessions`' only SELECT policy required a participant row, so a creator missing one couldn't SELECT their own room; since PostgREST issues `DELETE ... RETURNING` and RETURNING is subject to the SELECT policy, 0009's creator-delete policy silently deleted nothing. Policy widened to "participant **or** creator". Non-participants remain fully locked out.
- `0012_dish_matches.sql` — **the multi-dish model** (see product decision 5 above). New `dish_matches` table (`session_id`, `restaurant_name`, `dish_name`, `matched_at`, unique on `(session_id, restaurant_name, dish_name)`), SELECT-only RLS via the existing `is_room_participant()` helper. **No client write policy at all** — the only writer is the SECURITY DEFINER trigger, so a participant cannot forge "the table agreed on this". `check_dish_swipe_match()` rewritten: on unanimity it `insert ... on conflict do nothing` into `dish_matches` and **leaves `swipe_sessions` completely alone** (the `>= 2` participant floor and current-participants-only counting from 0009 are unchanged). Added to the `supabase_realtime` publication **and** given `replica identity full` — both are required, publication membership alone delivers silently nothing. Deliberately does NOT drop `matched_restaurant_name`/`matched_dish_name` or narrow the status check constraint: dropping columns on a live database is riskier than ignoring them, so the app simply stopped reading/writing them.

- `0013_harden_rls_and_validation.sql` — **the security hardening pass; NOT YET APPLIED, the user must run it.** Blocks a creator from forging the group's match (guard trigger on `swipe_sessions`), removes the client INSERT policies on `room_participants` and `swipe_sessions` (self-joining any room by uuid; malformed/squatted codes), normalises and bounds `profiles` (self-set `is_guest`, empty/10k-char `display_name`, 500-entry `dietary_restrictions`), adds length/shape constraints (all `NOT VALID`, deliberately), makes `join_room_by_code()` signed-in-only and throttles wrong-code guesses, and caps rooms-per-creator-per-hour. Full detail per block in the file's own header comments, summarised below.

- `0014_retention_loop.sql` — **Phase 4, the retention loop; NOT YET APPLIED, the user must run it.** Two new tables and nothing else: `session_feedback` (one row per session per member, unique on that pair so feedback is editable not duplicable; room-wide SELECT via `is_room_participant()`, own-row-only write, own-row DELETE, a guard trigger freezing the identity columns and server-setting `updated_at`, plus Realtime) and `saved_restaurants` (owner-private favourites, `source_session_id` as `ON DELETE SET NULL` so a closed room can't delete somebody's list, `website` CHECK-constrained to `^https?://` because it is rendered as an href and comes from a third-party API). Constraints here are normally validated, **not** `NOT VALID` — that flag exists to avoid a validation scan tripping over pre-existing junk, and these tables are created empty. **History and async rooms deliberately added no tables** — blocks C and D of the file are rationale-only, documenting what is queried instead and why a `last_seen_at` column on `room_participants` was rejected. Block E adds the one index the new queries need: `room_participants (user_id, joined_at desc)`, since the PK only indexes the room → members direction and nothing before this ever asked "which rooms am I in".

- `0015_monetization.sql` — **Phase 5, monetization; NOT YET APPLIED, the user must run it.** Independent of both 0013 and 0014 (purely additive, redefines nothing either of them touches), so it can be run before or after them. Two tables and two views. `sponsored_placements`: restaurant identity as plain text (no restaurants table exists), optional cuisine/country/lat-lon-radius targeting, a `starts_at`/`ends_at` flight window, `is_active`, and `priority` for ranking; the SELECT policy exposes **only rows that are live right now** (a user has no business seeing the commercial calendar) and there are **no INSERT/UPDATE/DELETE policies at all**, so only `service_role` can write — restaurant-side accounts don't exist yet, and a client-writable path would let any user feature themselves for free in other people's results (same reasoning as `dish_matches` in 0012). Note recorded in the file: **RLS is row-level, never column-level**, so any commercially sensitive field added later (rate card, spend, contract) must go on a separate service-role-only sibling table, not on this one. `monetization_events`: append-only click/impression funnel, `user_id` defaulted to `auth.uid()` and pinned by RLS, own-rows-only SELECT (a co-participant policy would turn "which takeaway did you click" into shared data), no UPDATE/DELETE policies. Both reporting views are `revoke`d from `anon`/`authenticated` and granted to `service_role` only. Realtime deliberately **not** enabled on either table — nothing in the UI reacts live to an ad campaign or someone else's click.

**Dietary tag vocabulary** (shared contract between the cuisine seed data and the profile restriction data — keep these in sync, don't let them drift): `vegetarian`, `vegan`, `halal`, `gluten-free`, `nut-free`, `dairy-free`, `shellfish-free`. A cuisine is eligible for a room if its `dietary_tags` is a superset of the union of all participants' `dietary_restrictions` in that room.

## QA blocker fixes

Found by driving the built app as two real users, then fixed and given tests. Ordered by how much damage each could do.

### 1. An AI suggestion could bypass the dietary/allergy filter (the P0)

**The bug, reproduced:** in a room with a halal + gluten-free member the deck correctly narrowed 9 cuisines → Indian only. Rejecting Indian and pressing "Get AI Suggestions" appended an **unvetted "Chinese"** card, and the room matched on it. Product guarantee #2 failed at precisely the moment it exists for — a stalled room is when people press that button.

**Cause:** an AI name that doesn't resolve to a `cuisines` catalog row became a synthetic card via `syntheticCuisineFromName()` with `dietaryTags: []`, and nothing filtered those. `dietaryTags: []` was being read as "no conflicts" when it actually means "nobody has vetted this".

**Fix — two independent gates**, because the deck is where the promise is kept:

- **Server-side (quality).** `/api/suggest-cuisines` takes a new **optional** `allowedCuisines: string[]`. When present and non-empty the prompt becomes "choose ONLY from this list", and anything the model returns that isn't in it is dropped before responding. The whitelist is enforced on the **fallback path too** — otherwise "Gemini is down" silently becomes "the dietary filter is off", since the DB/hardcoded fallbacks know nothing about the room's restrictions. Backward compatible by construction: the other three request fields and the response shape are untouched, and an omitted or empty `allowedCuisines` behaves exactly as before (asserted).
- **Client-side (the actual boundary).** `resolveSuggestedCuisines()` re-checks every returned name locally. The endpoint is unauthenticated and lives across a network call, so the deck does not take its word for it. A name that resolves to a catalog row must still pass the room's dietary filter; a name that resolves to **nothing** is dropped outright whenever the room has any restriction. Rejections are *returned*, not swallowed, so the UI can say why nothing appeared — silently adding nothing and silently adding something unsafe look identical to a user, and neither is acceptable.

An **unrestricted** room still gets synthetic `ai-<slug>` cards, so the stalled-room rescue and the `ai-*` `cuisine_id` path the security suite depends on both stay alive.

**`src/lib/suggestion-safety.ts` is a new file and deliberately so.** The gate can't live in `cuisines.ts` because that pulls in `supabase/client.ts` (a browser client + `import.meta.env`), which a Node test can't import. Moving it out — one dependency, `./dietary.ts` — lets `scripts/test-dietary-safety.mjs` import and execute **the real shipped function** under Node 24's type stripping. For a safety boundary, asserting against a mirrored re-implementation (the way `_shared.mjs` mirrors the SQL surface) proves nothing: the two can drift, and the drift *is* the bug. `cuisines.ts` re-exports everything, so callers still `import { resolveSuggestedCuisines } from "@/lib/cuisines"`.

The `import { ... } from "./dietary.ts"` extension in that file is load-bearing — Node's ESM resolver requires it, and `tsconfig.json` gained `allowImportingTsExtensions` for it. Don't tidy it away.

**Proof it's a real test, not a decorative one:** reverting just the gate's `if (restricted) { rejectedUnvetted.push(name); continue; }` turns the suite red — `33 passed, 6 failed`, with `expected [], got [{"id":"ai-chinese",...}]`. Restored, it's `39 passed, 0 failed`.

### 2. The dish deck dead-ended, and every restaurant had the same menu

`dish-swipe-area.tsx` built its deck from `cuisines.find(c => c.id === cuisineId)?.dishes ?? []`. Any `ai-*` cuisine id matches no catalog row, so the deck was literally `[]` and a group that matched on an AI suggestion hit "That's the whole menu / Nobody's reached unanimity here yet" **forever** — a dead end at the end of the happy path. Quieter second bug: even for a catalog cuisine, every restaurant showed the same 5 generic dishes.

Now wired to `POST /api/restaurant-menu` (`src/lib/restaurant-menu.ts`). Catalog dishes are demoted to an **offline fallback only**, and the UI says so when it's using them rather than passing stand-ins off as the restaurant's real menu. Loading, error and `429` each get their own state with a working action — an empty deck is the dead end being removed, so a failure must never be swallowed into `[]`. Unlike `ai-suggestions.ts`, this client deliberately **does not** swallow failures.

**The room-consistency problem this creates, and the deliberate answer:** the menu is generated, so two members can be served slightly different dish lists, and `dish_swipes` are scoped by `(restaurant_name, dish_name)` — a dish only one member can see could never reach unanimity. The deck is therefore the **union** of my fetched menu and every dish name the room has already swiped on or agreed at this restaurant (both already synced over Realtime). A dish someone else sees enters my deck the moment they vote on it, and the group converges without new storage. The proper fix is persisting the menu per `(session, restaurant)`; that needs a migration, which this pass could not write.

### 3. The remaining findings

- **"Leave room" could destroy the wrong room.** `room-controls.tsx`'s `handleLeave()` fell back to `clearActiveRoom()` when it couldn't resolve `room.id` — wiping the single global `foodswipe_active_room` key regardless of which room it referred to. With ZJHM active, visiting `/match/italian?room=ZZZZ` and pressing Leave destroyed the ZJHM record while leaving the user a participant of ZJHM server-side, still inflating its unanimity denominator, with no "my rooms" list to recover from. The control now renders **only** for a room `isRoomParticipant()` confirms you're in, `id` is non-nullable, and there is deliberately **no else branch**. `clearActiveRoomIfMatches(roomId)` (new, in `rooms.ts`) replaces the blunt version everywhere; `clearActiveRoom()` is now reserved for discarding a cache entry that no longer resolves at all.
- **Match reveal fabricated decisions.** `match-reveal.tsx` never checked `room.status === "matched"` or `matchedCuisineId === cuisineId`, and never validated the slug — `/match/not-a-real-cuisine-🍕?room=X` rendered "You all want Not a real cuisine 🍕!" on a waiting, zero-swipe room. A shared link could convince a group of a decision that never happened. Now: slug shape validated, and distinct honest states for "no decision yet", "your group picked something else" (with a link to the real one), and an unrecognised slug. A match is a server verdict; this page reports it, it never asserts one.
- **A successful match cleared the active room**, so "Back to the room" landed on an empty dashboard — on the happy path. Both `swipe-area.tsx` and `rooms-dashboard.tsx` now `saveActiveRoom()` on match instead. The room is still live after matching: the group still has to pick a restaurant and swipe dishes.
- **Room deleted under you → stale UI.** `subscribeToRoom()` guarded on `payload.new && "id" in payload.new`, which is false for a DELETE (`payload.new` is `{}`), so deletions were dropped on the floor while the `dish_matches` cascade silently emptied the agreed list. `onSessionDeleted` is handled first now, and both `/swipe` and the dish page render an explicit "This room was closed" state with a way out.
- **Supabase errors were swallowed.** Handlers tested `err instanceof Error`, which is **false for `PostgrestError`** (a plain object) — exactly when the real message was most useful. `Room "QQQQ" not found.` became "Could not join the swipe room." `src/lib/errors.ts`'s `errorMessage()`/`errorCode()` are now applied across the room/swipe/join handlers. The `PGRST116 → "Room not found."` mapping in `rooms.ts` is preserved (0013 makes `join_room_by_code()` return zero rows rather than raise).
- **Redirect reasons were never seen.** Code toasted and then immediately set `window.location.href`, and a full navigation tears down the document *and* the toast. All three paths (not-a-member, room-not-found, sign-in-required) now carry a `?notice=` **code** — never text, since a page that rendered arbitrary query-string text would be a shareable way to put words in the app's mouth — consumed and stripped once on arrival (`src/lib/notices.ts`).
- **Signed-out deep links lost the room code.** `/swipe?room=ABCD` signed out → `/rooms` → `/login`, which hardcoded a redirect to `/rooms`, so an invited friend could never follow a swipe link. The destination now survives the auth round trip via `?redirect=`, including through the OAuth callback. Only same-origin, path-absolute values are honoured — otherwise `?redirect=` is an open redirect handing a freshly-authenticated user to someone else's site with this app's branding behind them.
- **`AppHeader.astro` showed "Log out" and room controls to signed-out users** (static markup, no auth branch) — most self-contradictory on the guest-invite page, which promises "no account needed" directly under an offer to log out. The nav is now an island (`header-nav.tsx`). ## Key engineering patterns established (reuse, don't reinvent)

- **RLS recursion**: any policy that needs to check "is this user a participant of room X" should call the existing `is_room_participant()` SECURITY DEFINER function, not write a fresh self-join policy.
- **Cross-user data exposure**: never add a raw co-participant SELECT policy on a table with sensitive columns (like `profiles.phone`). Use a SECURITY DEFINER RPC that returns only the safe columns, following `get_room_profiles()`.
- **Astro + Supabase SSR cookies**: `src/lib/supabase/server.ts` has the working `AstroCookies` adapter for `@supabase/ssr` (Astro has no cookie-enumeration API, so `getAll` parses the raw `Cookie` header via `parseCookieHeader`). Reuse this client factory, don't rewrite it.
- **Astro output mode**: static by default; any page needing server-side auth checks, or that reads `Astro.url.searchParams`/other per-request data, must set `export const prerender = false` and the project needs the `@astrojs/node` adapter (already installed) for that route to render per-request. **Trap to check for**: a static page that reads the query string at build time (no query string exists then) silently bakes in a wrong permanent result — either flip it to `prerender = false`, or read the query string client-side inside a React island via `window.location.search` if the page can otherwise stay static (Phase 2's `rooms/join.astro` did the latter; `swipe.astro` did the former — see Phase 2 detail above for why each).
- **RLS "can't look up a row I'm not yet allowed to see" (join-by-code pattern)**: when a client needs to discover/act on a row it doesn't have access to *yet* (e.g. joining a room by code before being a participant), don't add a permissive SELECT policy to work around it — add a narrow SECURITY DEFINER RPC that performs the lookup and the one specific write it's meant to allow, then returns only the safe fields, same shape as `get_room_profiles()`. See `join_room_by_code()` in `0005_room_join_rpc.sql`.
- **Server-side match/decision triggers**: any "the group unanimously agreed on X" logic must be a SECURITY DEFINER Postgres trigger, not client-computed — a client-computed match is trivially fake-able by a single dishonest participant. See `check_swipe_match()`/`check_dish_swipe_match()`. The trigger being SECURITY DEFINER also matters practically: it needs to update `swipe_sessions.status` regardless of whether the swiper who completes the match happens to be the room's creator, and the "only creator can update status" RLS policy would otherwise block a non-creator from doing that update directly.
- **Realtime**: adding a table's RLS policies is not sufficient for `postgres_changes` subscriptions to fire — the table must also be added to the `supabase_realtime` publication (`0008_enable_realtime.sql`). Do this in the same migration set that creates the table, not as an afterthought.
- **RLS is row-level, so column immutability needs a trigger**: a policy can say *who* may update a row, never *which columns* or *which values*. Any column that is a server verdict (`swipe_sessions.matched_cuisine_id`, `status`, `code`, `profiles.is_guest`) needs a BEFORE UPDATE guard trigger, not a cleverer policy. The trusted writers (SECURITY DEFINER RPCs and match triggers) announce themselves with a transaction-local GUC — `perform set_config('app.foodswipe_trusted', 'on', true)` immediately before the write and `'off'` immediately after — because triggers fire for definer functions too. See `guard_swipe_session_update()` in 0013.
- **Probing RLS: never use `.insert().select()`**. PostgreSQL applies SELECT policies to a RETURNING clause and reports the failure with the *same* `42501 new row violates row-level security policy` text as a WITH CHECK violation. A write that looks blocked may have been perfectly legal and only failed on the way back — that is exactly how the "anyone can join any room by uuid" hole hid in plain sight. Probe writes with no RETURNING, then read back separately.
- **`raise exception` rolls back your audit write**: any RPC that wants to *record* a failed attempt and *then* refuse cannot raise — the exception aborts the transaction and discards the record, and PL/pgSQL has no autonomous transactions. Return an empty result set instead and let the caller's `.single()` turn it into an error (see `join_room_by_code()`'s throttle in 0013, and the PGRST116 mapping in `src/lib/rooms.ts`).
- **AI calls**: no Genkit in this rebuild — direct Gemini REST calls only, kept lightweight. Same for restaurant search (direct Geoapify fetch, no wrapper). Phase 3 built the concrete pattern: `src/lib/ai/gemini.ts`'s `generateGeminiJson<T>()` (model `gemini-2.5-flash`, `responseSchema` for structured JSON, `thinkingConfig.thinkingBudget: 0` for these non-reasoning tasks) — reuse it, don't re-implement the fetch per endpoint. Any call from client code to a teammate's API route (e.g. Phase 2's call to `/api/suggest-cuisines`) must swallow failures into a safe empty/default result — never let a 404 or network error block the calling UI.

## Security & abuse-resistance pass

An adversarial pass over the backend, run as four real users through the anon key — the same position an attacker with the public bundle is in. `scripts/test-security.mjs` is the permanent record: 87 assertions covering privilege escalation through the SECURITY DEFINER RPCs, data tampering, match forgery, constraint gaps, races, lifecycle/orphans, and the four public API routes. Every assertion in it was written against an **observed** result on the live project, and each finding's real "before" output is quoted in the migration/route comment that fixes it.

**Found and fixed in code (live, verified — no migration needed):**
- **PostgREST filter injection** in `/api/restaurant-menu`'s DB fallback. It built its filter by interpolation: `.or(`id.eq.${cuisine.toLowerCase()},name.ilike.${cuisine}`)`. In PostgREST's grammar `,` separates conditions and `.` separates column/operator/value, so a `cuisine` containing either is not a value but more query — verified live: the payload `nope,dietary_tags.not.is.null` returned **9 rows** (the entire catalog) instead of 0. Rewritten as separate `.eq()` / `.ilike()` calls, which pass their arguments as values. The vulnerable and fixed forms are both exercised in section 09 of the suite, because the fallback only runs when Gemini is down and can't be forced from outside.
- **No input bounds on any of the four routes.** Unlimited body size, unlimited array length, unlimited string length — all forwarded to paid Gemini/Geoapify calls. Now: 16 KB body cap, per-field length caps, array item caps, `finiteNumber()` range checks on coordinates (`typeof NaN === "number"` and `latitude: 999` both used to reach a live Geoapify query). Model **output** is capped too — a dish name from Gemini becomes a `dish_swipes.dish_name` in everyone's deck.
- **No rate limiting.** `src/lib/api/guard.ts` adds a per-IP fixed-window limiter (15s window; 6 requests for the two Gemini routes, 8 for Geoapify, 25 for `delivery-links`). Honest scope, documented in the file: it is in-process memory, so on Vercel it is per-instance, and it is a backstop for a platform limiter, not a replacement.
- **Gemini API key moved from the query string to the `x-goog-api-key` header** (`src/lib/ai/gemini.ts`). A key in a URL ends up in thrown fetch errors and every log line that prints them, and every caller logs the error before falling back. The suite asserts no server-side key appears in any response across six endpoints/error paths.
- **Prompt injection** via `restaurantName`/`cuisine`: mitigated (single-line inputs, hard caps, fenced-and-labelled data, bounded output), and assessed honestly rather than inflated — the response is schema-pinned, goes only to the caller who sent the payload, is not stored, and the prompt contains no secret and no tool. Worst realistic case is "you made the model write your own dish names back to you". The mitigations that matter here are the boring ones that protect the bill.

**Found, fix written, WAITING ON THE USER to run `supabase/migrations/0013_harden_rls_and_validation.sql`** (these are the 18 red assertions in `test-security.mjs`, all tagged `[needs 0013]`; the suite prints a banner telling you so):
- **A room creator could forge the group's verdict.** `update swipe_sessions set status='matched', matched_cuisine_id='japanese'` with **zero swipes cast by anyone** — and the other member's client faithfully rendered it over Realtime. The "a match is a server verdict, never a client claim" guarantee was defeated by the one participant most likely to want to. 0001's "only creator can update status" policy is row-level: it constrains *who*, never *which columns* or *which values*. The creator could also rewrite `code`, invalidating every share link already handed out. Fixed by a BEFORE UPDATE guard trigger; client updates may now only move `status` between `waiting` and `swiping`.
- **Any authenticated user could join any room knowing only its uuid**, with no code and no invitation — `room_participants`' INSERT policy was `with check (user_id = auth.uid())`, i.e. "you may add yourself", with nothing about the room. Membership is the key to every other policy in the schema, so this was a self-service grant of the room: read the room, the participant list, everyone's `display_name` + `dietary_restrictions`, and write swipes — plus a permanent match block, since an uninvited body inflates the unanimity denominator and never votes. Client INSERT policy dropped; `create_room()` / `join_room_by_code()` are SECURITY DEFINER and unaffected.
- **An unauthenticated room-code oracle.** Signed out, with only the public anon key: a real code returned `[23502] null value in column "user_id"...` while a fake one returned `Room "QQQQ" not found.` — two distinguishable answers, so "does room XXXX exist?" was askable 456,976 times by someone with no account. Measured signed-in guess rate was 9.9–12.8/s sequential (**~10–13 h for a full sweep**, far less in parallel), and every hit auto-joins the guesser. Fixed: signed-in callers only (kills the anonymous oracle) plus a 12-wrong-codes-per-minute throttle (~24 days per account per sweep). Risk stated plainly: this is display names, dietary tags and dinner plans, not credentials — but "sweep the space overnight and land in every live room" was a real griefing/scraping capability available anonymously. The proper fix is a bigger code space, which is a product change.
- **`profiles` was self-serve.** `is_guest` — the flag the "Guest" badge trusts — was settable by its owner; `display_name` accepted `""` and 10,000 chars; `dietary_restrictions` accepted 500 junk entries. None of these is self-harm: `get_room_profiles()` publishes all three to every co-participant, and the dietary filter unions everyone's restrictions, so 500 junk tags empties the deck for the whole room. Fixed by a normalising guard trigger (trim, default to `Guest`, truncate at 60, cap the restriction array, freeze `is_guest`).
- **No length bounds in the DB either**: 10,000-char `cuisine_id`, `restaurant_name`, `dish_name` all accepted, all echoed room-wide. Added as `NOT VALID` CHECK constraints — deliberately, so a stray legacy row can't abort the migration on a live database while new writes are still enforced.
- **Malformed room codes could be inserted directly** (`ab1!`, `abcd`, `"  z "`, `日本語人` all succeeded) — and `join_room_by_code('日本語人')` really joined that room, while a lowercase-coded room is permanently unjoinable (the RPC upper()s its input) and holds a code hostage. Fixed by dropping the direct INSERT policy, a `^[A-Z]{4}$` shape constraint, and a one-time cleanup of the malformed rows.

**One contract change worth knowing about**: `join_room_by_code()` now reports "no such room" by returning **zero rows** instead of raising. It has to — `raise exception` aborts the transaction, which would roll back the very row that records the failed attempt, so the throttle would have counted nothing forever while looking correct. `src/lib/rooms.ts` maps PostgREST's resulting `PGRST116` back to the same `"Room not found."` message it always threw, so nothing changes for the user. (This is the kind of bug that only shows up if you re-read your own migration before shipping it — worth doing here, since nobody in this project can execute a migration to find out.)

**Considered and deliberately NOT changed:**
- **No FK from `swipes.cuisine_id` to `cuisines.id`.** It looks like an obvious missing constraint, but the AI match-fallback deals cards for cuisines that are deliberately not in the catalog (`syntheticCuisineFromName()`'s `ai-<slug>` ids) and a room must be able to match on one. An FK would break the feature that exists to rescue a stalled room. A bogus `cuisine_id` also isn't an attack: every participant has to right-swipe the same one, and a room that unanimously agrees on a nonsense card has agreed. The suite asserts the synthetic id still works so nobody "fixes" this later.
- **A plausible-looking set of dietary restrictions can still empty a room's deck.** Indistinguishable from an honest user with hard requirements — a product question (the room needs an override), not an access-control one.
- **Room codes stay 4 letters.** Enumeration is throttled rather than eliminated; widening the code space touches the UI, the share links and every existing room.
- **No TTL/cleanup sweep for dead rooms.** Rooms are never deleted, so the 456,976-code space only fills up. `create_room()` now caps a creator at 100 rooms/hour as a speed bump; the real fixes (bigger code space + expiry) are product work. The cap is deliberately not exercised by the suite — proving it would mean creating 100 rooms per run, which is the abuse it exists to stop.
- **Swipes have no DELETE policy at all**, so nobody (including the owner) can delete a swipe. Re-swiping updates in place, so the app never needs it; leaving it closed is the safer default.
- **Verified-safe, left alone**: impersonating another user's swipe or participant row, flipping/deleting another member's swipe, deleting another member's `room_participants` row, a departed member flipping a stale swipe, direct `dish_matches` inserts, editing another user's profile, `get_room_profiles()` with null/zero/foreign/injection-shaped uuids, and simultaneous double-unanimity (the room matches exactly once — the second update re-checks the guard clause and no-ops). All were probed and all held; they now have permanent assertions.

**Cascade/lifecycle behaviour is sound** and now asserted: a creator deleting a room mid-session cascades away participants, swipes and `dish_matches`, the other members read the room as `null` (the UI's "This room isn't available" state) and their next write fails cleanly with an RLS error rather than resurrecting anything.
