Food Swipe · design language · v1 · desktop (1280–1600px)
Same tokens, same motion vocabulary — desktop earns its width by showing the group, not by growing the card.
The swipe card is capped at 460px and stays centered: mouse-drag ergonomics don't scale with viewport. What the extra width buys is persistent context — who's in the room, what they've voted, where you are in the rounds — which on mobile has to be compressed into a progress bar.
DESKTOP DELTAS FROM THE MOBILE SYSTEM
grid: 12 col, 1240px max, 24px gutter, page pad 40px (≥1280) / 32px (1024–1279)
card cap 460px · rails 280px (left) + 300px (right), both collapse below 1120px into the mobile stack
type scales up one step at the display end only: H1 32→44, dish title 34→40. Body stays 15–16px
hover states exist here and do real work (mobile has none): card lift, row tint, button darken
keyboard is a first-class input: ← pass, → like, ↑ super-like/save, Z undo — hinted persistently under the stack
touch targets relax to 40px minimum (pointer), except the primary swipe controls which stay 64/72px

STATE RULES
skeleton after 300ms, not before; geometry identical to the loaded card so nothing reflows

no spinner over 1s: past that it becomes a skeleton or a progress statement
